# PCServer 日志持久化设计

## 背景

`PCServer/attach` 已使用 `tracing` 输出结构化日志，但当前仅写入终端。全局普通项目日志规范要求同时写入终端和文件、按本地日期滚动、保留 30 天、输出启动与滚动 Banner，并避免业务线程直接进行文件 I/O。

## 范围

- 仅调整 `PCServer/attach` 的 `tracing` 初始化与其测试。
- 复用现有 `tracing` 日志调用和 `RUST_LOG` 过滤。
- 不改变 CLI 的 JSON/会话 ID 标准输出，也不调整移动端平台日志桥接。

## 方案比较

1. 仅补终端时间戳：改动最小，但不满足文件持久化、滚动与异步写入要求。
2. 使用 `tracing` 的自定义 writer：可由后台线程按 FIFO 队列批量写入精确命名的每日文件，并在写入线程完成 30 天清理；满足全部要求。
3. 另建独立日志服务：超出本地 CLI 的需求，增加通信与运维成本。

采用方案 2。

## 设计

- `init_logging` 创建一个后台日志写线程，并将 `tracing_subscriber` 的格式化输出同时写至终端和该线程的队列。
- 日志格式统一为本地时间戳、`[E]/[W]/[I]/[D]` 等级和消息；`RUST_LOG` 继续控制过滤等级。
- 文件目录为系统临时目录下的 `attach/logs`；文件名为 `attach-YYYY-MM-DD.log`。后台线程按本地日期切换文件，在启动与日期切换时写入 Banner（名称、版本、系统名称和系统版本）。
- 后台线程按 FIFO 接收日志，将两秒内收到的内容合并写入一次；每次切换文件后删除超过 30 天的 `attach-YYYY-MM-DD.log`。
- 进程结束时通过 guard 发送关闭信号并等待后台线程完成已排队日志的写入。

## 错误处理与验证

- 日志目录创建、文件打开和写入失败不得影响 CLI 主流程；终端日志仍可用。
- 增加单元测试，验证文件名日期解析与保留期判断，避免依赖系统时钟和文件系统时序。
- 执行 `cargo fmt --all`、`cargo test -p attach`、`cargo clippy --all-targets --all-features`。
